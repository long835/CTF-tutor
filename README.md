# CTF-tutor

> Learn the vulnerability. Understand the exploit. Capture the flag.

CTF-tutor is a practical learning tool for working through Capture The Flag challenges.

Instead of focusing only on getting the flag, the project focuses on understanding **why a vulnerability exists, how to identify it, and how the exploit works**.

---

## What it does

CTF-tutor takes a challenge or collection of learning material and helps break it down into smaller concepts.

The current system focuses on:

* Challenge decomposition
* Concept identification
* Explanation of technical concepts
* Source/resource ingestion
* Retrieval of relevant information
* Difficulty/depth guidance
* Challenge-oriented learning
* Static analysis utilities
* Automated tests

# How it works

The basic workflow is:

```text
             CTF Challenge
                   │
                   ▼
            ┌─────────────┐
            │  Ingestion  │
            └──────┬──────┘
                   │
                   ▼
          ┌─────────────────┐
          │   Decomposer    │
          └────────┬────────┘
                   │
                   ▼
          ┌─────────────────┐
          │    Retriever    │
          └────────┬────────┘
                   │
                   ▼
          ┌─────────────────┐
          │    Explainer    │
          └────────┬────────┘
                   │
                   ▼
          ┌─────────────────┐
          │   Synthesizer   │
          └────────┬────────┘
                   │
                   ▼
             Tutor Response
```

The important part is not simply producing an answer.

The goal is to break down the problem into concepts that the learner can understand and use on the next challenge.

# Installation

Clone the repository:

```bash
git clone git@github.com:long835/CTF-tutor.git
cd CTF-tutor
```

Install the dependencies:

```bash
pip install -r requirements.txt
```

Install [Ollama](https://ollama.com) and pull a chat model and an embedding
model:

```bash
ollama pull qwen3:8b            # or a bigger model if your hardware allows
ollama pull nomic-embed-text    # used for archive retrieval
```

Configuration is loaded from a `.env` file, so each user can point at their
own Ollama server without editing code. Copy the example and adjust it if
needed (the defaults match a local `ollama serve`, so this step is optional
unless your Ollama runs elsewhere):

```bash
cp .env.example .env
```

```
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=qwen3:8b
OLLAMA_EMBED_MODEL=nomic-embed-text
```

(Optional, for `pwn`/`rev` static analysis) install the CLI recon tools --
each one is used if present and skipped gracefully if not:

```bash
sudo apt install binutils file binwalk exiftool
pip install checksec.py
```

(Optional, for `--decompile`) install [Ghidra](https://ghidra-sre.org/) and
point `GHIDRA_INSTALL_DIR` at it -- see the **Decompilation** section below.

# Usage

Index your archive of past solved challenges (once, and again any time you
add entries to `data/archive/`):

```bash
python ingest.py
```

Run the full pipeline against a new challenge:

```bash
python main.py "A login portal issues JWTs signed with RS256. \
The admin panel trusts the role claim in the token." \
    --category web --file ./challenge_files/app.js --depth approach
```

`--depth` is optional and tiered: `name` -> `approach` -> `commands` ->
`walkthrough`. Omit it to get decomposition, retrieval, cross-referencing,
and explanations without any hints at all. `--category` is also optional --
if you leave it out, `classifier.py` auto-detects it from the description
(a fast keyword heuristic first, falling back to an LLM call only when the
heuristic is ambiguous).

Prefer to reveal hints one level at a time instead of getting the whole
ladder at once? Use `--interactive` instead of `--depth`:

```bash
python main.py "..." --category pwn --file ./chall --interactive
```

It'll ask before showing each level (`y` to reveal and move up a level,
anything else to move to the next sub-problem, `q` to stop).

Every `run` is logged to `data/history.jsonl` automatically (pass
`--no-history` to skip). Use the `history` subcommand to look back:

```bash
python main.py history              # list recent sessions
python main.py history -n 20        # last 20 instead of the default 10
python main.py history --summary    # technique-frequency across all sessions
```

Search or browse your archive directly, without going through the full
pipeline:

```bash
python main.py search "jwt alg none bypass"     # semantic search (needs ingest.py run first)
python main.py search "ssrf" --category web -n 3

python main.py list                              # everything on disk, grouped by category
python main.py list --category pwn
```

Run `python main.py --help` for the subcommand list, or
`python main.py <subcommand> --help` for a specific subcommand's flags. The
exact interface may change while the project is being developed.

# Performance / why a `run` sometimes feels slow

Almost everything expensive in this project is already native code, not
Python: Ollama's inference engine, chromadb's vector search, Ghidra's
decompiler, `binutils`. Python here is orchestration and HTTP calls, so the
actual bottleneck is nearly always the model itself -- specifically, its
**cold-load**: the first request to a model Ollama hasn't used recently can
take tens of seconds (sometimes much longer on CPU-only setups) while it
loads into RAM/VRAM, and every request after that is fast until it idles
out again. Left unhandled, that delay lands invisibly on whichever pipeline
stage happens to go first, which is what makes a cold server feel like it's
randomly stalling rather than predictably working.

What's done about it:

* **Warm-up.** `run` pings the model once, up front, with a visible spinner
  ("Waking up ... while it loads") before touching anything else -- one
  predictable wait instead of several random ones. Skip it with
  `--no-warmup` if you know the model's already loaded (e.g. running
  several challenges back to back).
* **Visible progress.** Each stage prints a status line
  (`[1/4] Decomposing...`, `[2/4] Searching your archive...`, ...) instead
  of the CLI going silent until the very end.
* **Concurrency.** Independent Ollama calls -- one per sub-problem for
  retrieval/explanations, one per hint level for the hint ladder -- run
  concurrently via a thread pool (`concurrency.py`) instead of one at a
  time. Real speedup depends on your Ollama server's own
  `OLLAMA_NUM_PARALLEL` setting; if it only serves one request at a time,
  this still removes Python-side serialization overhead and lets calls
  queue immediately rather than waiting on each other's full round trip
  first.
* **Clean failure.** If Ollama becomes unreachable at any point in a run,
  you get one `error: ...` line and a non-zero exit code, not a raw
  traceback.

`llm_client.call_ollama()` also supports `stream=True` with an `on_token`
callback for live token-by-token output, for anything that wants to show a
genuinely prose (non-JSON) reply as it generates rather than waiting for
the full response.

# Decoding blobs (CyberChef-style, no Node.js/CyberChef install needed)

```bash
python -m tools.decode_toolkit "ZmxhZ3t0ZXN0fQ=="
# [0] recipe=['from_base64'] printable=1.00
#     flag{test}

python -m tools.decode_toolkit --recipe from_base64,gunzip "<base64 blob>"
```

`tools/decode_toolkit.py` is a small, dependency-free Python
reimplementation of the CTF-relevant subset of CyberChef's operations:
base64, hex, URL encoding, ROT13/Caesar, XOR (including single-byte
bruteforce), gzip/zlib, a `run_recipe()` chain composer, and a
`magic_decode()` auto-detector that tries the likely candidates the way
CyberChef's Magic wand does. If you specifically want the real CyberChef
UI, run it locally (https://github.com/gchq/CyberChef) instead -- this
module is the fast, scriptable subset for automated/LLM-driven use.

# Decompilation (optional, requires a local Ghidra install)

```bash
export GHIDRA_INSTALL_DIR=/path/to/ghidra_11.x_PUBLIC
python main.py "..." --category pwn --file ./chall --decompile
```

`tools/ghidra_headless.py` drives Ghidra's `analyzeHeadless` (via the
bundled `tools/ghidra_scripts/DumpDecompiled.py` post-script) to add a
decompiled listing to the evidence the decomposer sees for `pwn`/`rev`
files. Off by default since a real headless analysis pass takes a while;
`--decompile` opts in. Without Ghidra installed this degrades gracefully
to a one-line notice instead of failing the run, same as the other static
analysis checks.

# Example

A learner encounters a stack-based buffer overflow.

Instead of jumping directly to:

```text
FLAG{...}
```

the tutor should guide the learner through questions such as:

```text
1. Where is user-controlled input stored?

2. How large is the buffer?

3. What happens when the input exceeds the buffer?

4. What value is overwritten?

5. How can the overwrite offset be determined?

6. Which memory protections are enabled?

7. What control-flow technique is appropriate?

8. How can the final payload be constructed?
```

The learner should understand the process rather than simply copy a solution.

# Philosophy

CTF-tutor is built around a simple idea:

> **Don't just solve the challenge. Understand why the solution works.**

A good CTF tool should help someone become less dependent on the tool over time.
